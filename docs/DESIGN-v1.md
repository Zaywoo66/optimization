# Memory Pilot v1.0 — проект дизайна

Статус: **на согласовании**. Этот документ не включает реализацию управления процессами. Цель v1.0 — улучшать отклик Windows под фоновой нагрузкой, а не обещать фиксированное снижение ОЗУ.

## Архитектура

- Rust workspace: `crates/core` (сбор метрик, автомат состояний, правила, журнал и откат), `crates/cli` (команды `snapshot`, `watch`, `apply`, `rollback`, `report`, `compare`) и небольшой нативный Win32 tray без тяжёлого webview. Расширение Brave остаётся на JavaScript: браузер загружает расширения именно в этом формате.
- Поток сбора метрик раз в секунду публикует снимок с отметкой времени. Отдельная логика вычисляет состояние `OK / CPU / MEMORY / DISK / MIXED`, затем выбирает подходящие *фоновые* процессы. Режим по умолчанию — только журнал решений (`--dry-run`); `--apply` включает действия. В tray есть Pause и Rollback.
- Состояния меняются с гистерезисом: предварительно вход после 5 последовательных секунд давления, выход после 15 секунд без него. Пороги задаются TOML-профилем и проверяются на целевой машине; краткие пики не вызывают переключений.
- Настройки и журнал лежат в `%LOCALAPPDATA%\MemoryPilot`. `config/default.toml` хранит профили `dev-agent`, `balanced`, `max-responsiveness`, объяснение каждого правила и список защищённых имён/путей. Никакой отправки данных или проверки обновлений по умолчанию.

## Сбор данных и выбор целей

- CPU и память: Windows API и `sysinfo`; commit charge/limit и доступная память. Диск: PDH с [`PdhAddEnglishCounterW`](https://learn.microsoft.com/en-us/windows/win32/api/pdh/nf-pdh-pdhaddenglishcounterw) для очереди, занятости и задержки диска. `\Memory\Page Reads/sec` отражает операции чтения при hard faults, **не точное число отдельных hard faults**; в отчёте будет назван именно так. Точный счётчик hard faults требует отдельного ETW-провайдера и не должен подменяться этой метрикой.
- Проба отклика: `WM_NULL` только текущему foreground окну через [`SendMessageTimeoutW`](https://learn.microsoft.com/en-us/windows/desktop/api/winuser/nf-winuser-sendmessagetimeoutw) с коротким тайм-аутом. Ошибка доступа/уничтоженное окно считаются «нет данных», а не зависанием. p95/p99 относятся к этой пробе, не ко всему пользовательскому вводу.
- При старте определяются RAM, версия Windows, логические/физические ядра и тип системного диска. P/E-классы и CPU Sets используются лишь при достоверном ответе Windows; иначе функция пропускается. Проверка оборудования не повторяется каждую секунду.
- Процесс выбирается только при давлении, совпадении с правилом по имени **и** подтверждённому пути, достаточной фоновой CPU/IO нагрузке и отсутствии защиты. Перед каждым действием заново проверяются PID + время запуска + путь, foreground окно, его предки и потомки, системные процессы, антивирусы/античиты и пользовательский protected list. Недоступная информация означает «пропустить», а не «разрешить».

## Действия и откат

1. Для подходящего процесса считать исходный `GetPriorityClass`, память через `GetProcessInformation(ProcessMemoryPriority)` и текущие CPU Sets через `GetProcessDefaultCpuSets`. Перед изменением записать журнал на диск, затем применить и проверить результат. [`SetPriorityClass`](https://learn.microsoft.com/en-us/windows/win32/procthread/scheduling-priorities) начинает с `BELOW_NORMAL`, не с `IDLE`.
2. [`SetProcessInformation(ProcessMemoryPriority)`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setprocessinformation) даёт ОС подсказку о приоритете страниц; это не «очистка RAM» и не гарантирует экономии памяти. EcoQoS применяется только когда его исходное состояние удалось прочитать и восстановить через [`GetProcessInformation`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocessinformation); при ошибке или несовместимом Windows этот механизм выключается. Действия применяются по одному, чтобы выявить эффект и ошибки.
3. CPU Sets — отдельный экспериментальный переключатель профиля. [`SetProcessDefaultCpuSets`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setprocessdefaultcpusets) не является жёстким affinity и не обещает резерв ядра для foreground. Применять только если есть безопасный набор ядер и получен исходный набор для отката.
4. На Pause, выходе, переходе в `OK` и `rollback` восстановить исходные значения. Журнал хранит PID, время запуска, путь, исходное и установленное значение каждого успешно изменённого атрибута. Откат сверяет идентичность процесса и восстанавливает только значение, которое всё ещё равно установленному Memory Pilot: так не перезаписываются более поздние изменения пользователя. После сбоя откат выполняется на следующем запуске до новых действий. При принудительном завершении самого Memory Pilot без перезапуска немедленный откат обещать нельзя; это будет явно написано в README.

## Не включать в v1.0 без отдельного решения

- `NtSetInformationProcess(ProcessIoPriority)`: внутренний интерфейс с риском несовместимости и без надёжной публичной пары чтения/восстановления исходного значения. В v1.0 вместо него измерять дисковое давление, снижать приоритет виновного фонового процесса документированным `SetPriorityClass` и **не обещать устранение I/O-лага**. Если бенчмарк покажет, что именно I/O остаётся проблемой, исследовать отдельный опциональный модуль на тестовой матрице Windows.
- Присоединение уже работающей задачи к Job Object для CPU cap: [Microsoft указывает, что связь процесса с job нельзя разорвать](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects). Это нарушает требование обратимости. Возможная будущая альтернатива — запуск *новой* задачи самим Memory Pilot в управляемом job, с явным согласием пользователя.
- `.wslconfig` и исключения Defender: только рекомендации и предлагаемое содержимое. Изменение конфигурации WSL — отдельное подтверждение, исключения Defender программа не создаёт.

## Проверка и этапы

1. Sampler + report: измерить цену сбора метрик, проверять отсутствующие/локализованные PDH-счётчики. 2. Автомат состояний с тестами гистерезиса. 3. Правила и dry-run с тестом нулевых изменений. 4. Применение, журнал и тест отката после искусственного сбоя; каждый атрибут получает свой проверяемый путь отката. 5. `bench/`: минимум пять парных прогонов без/с контроллером, медиана и разброс задержки пробы, stalls, доступной памяти, page reads и дисковой очереди. 6. Tray + README + CHANGELOG.

Каждый этап — отдельный коммит после тестов. Финальный gate: `cargo fmt --check`, `cargo clippy -- -D warnings`, тесты и GitHub Actions `windows-latest`; замер расхода самого Memory Pilot (<1% CPU, <20 МиБ RAM) и явный результат «в пределах шума», если улучшение не доказано. Тег `v1.0.0` ставится только после gate и бенчмарка. Запрещённые RAM-cleaner API, управление службами и запись в реестр не используются.
